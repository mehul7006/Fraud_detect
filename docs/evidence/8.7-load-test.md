# 8.7 Load test: POST /scan/url at 200 requests/second

Date: 2026-11-23. Tool: k6 0.54 (`tools/load/scan_url.js`, run by `tools/load/run.sh`).
Backend: the real jar in a throwaway container limited to **2 CPUs / 1 GB**, own PostgreSQL 16, on the dev PC.
20 test users, 7 kinds of links (safe, raw-IP APK, brand look-alike on .top, shortener, punycode, ...), random query
strings so nothing is served from a cache. 30 s warm-up at 100/s, then the measured run.

| Measured run (60 s at 200/s) | Result | Gate |
|---|---|---|
| Requests | 12 000 scans (+20 setup) = **200/s** | 200/s |
| p95 latency | **9.7 ms** (p50 6.0 ms, p99 23 ms, max 209 ms) | < 300 ms ✅ |
| Errors | **0 %** | < 1 % |
| Backend CPU | ~40 % of its 2 CPUs | – |

## What this does NOT cover
- **No Google Safe Browsing / VirusTotal calls** (keys left out on purpose: 12 000 lookups would spend the real quota).
  In production a link not yet in the cache adds Google's response time (typically 50–150 ms). Repeat this test on
  the production setup after 9.1, with the key, against a small URL sample.
- Dev PC, not the production machine or network.

## Lesson
The first two runs "failed" (p95 6.7 s, ~100/s): the warm-up step was broken, so the measured run hit a cold JVM and
requests queued. A real 30 s warm-up fixed it - always warm up before measuring.
